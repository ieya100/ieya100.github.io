# macOS → Samba: куда пропали мегабайты?

### Практический кейс: один ISO Windows 11, около 11 МБ/с по SMB и 54 МБ/с после настройки

**Результат:** передача одного и того же ISO (~8,1 ГБ) на основную SMB-шару ускорилась примерно в пять раз — с **10–12 МБ/с** до **~54 МБ/с**. Наиболее заметное улучшение совпало с включением `catia fruit streams_xattr` на Samba-сервере. Это результат конкретной конфигурации, а не универсальный рецепт для всех Mac и NAS.

## Стенд

- **Клиент:** MacBook Air с Apple Silicon, Wi‑Fi, штатный SMB-клиент macOS и Finder/терминальный `cp`.
- **Сервер:** Proxmox VE 9.2, непривилегированный Debian 13 LXC, Samba 4.22.
- **Хранилище:** зеркало ZFS из двух WD Ultrastar HC550 16 ТБ, сжатие ZSTD; каталог проброшен в контейнер через bind mount.
- **Сеть:** домашняя LAN; NFS в ходе этого эксперимента не тестировали.
- **Контрольный файл:** `Win11_25H2_EnglishInternational_x64_v2.iso`, около 8,1 ГБ.

Samba обслуживала шару `[shlak]` с путём `/srv/shlak`. Вторую, `[sync-test]`, создали только для испытаний, чтобы не менять рабочий ресурс наугад.

## Симптомы

Копирование большого ISO на NAS через Finder и `cp` шло со скоростью примерно **85–95 Мбит/с** по монитору активности macOS — это **10–12 МБ/с**, а не 85–95 МБ/с. Проблема воспроизводилась и на одном большом файле, поэтому объяснение «много мелких файлов» здесь не подходило.

Пример замера на Mac:

```bash
time cp ~/Downloads/Win11_25H2_EnglishInternational_x64_v2.iso \
  /Volumes/shlak/test.iso
```

Первоначальные быстрые тесты с файлом `mkfile 1g` оказались **неполностью сопоставимыми** с реальным ISO: такой файл заполнен нулями и очень хорошо сжимается ZFS. По нему нельзя достоверно оценивать скорость физической записи на HDD.

## Отделяем сеть, накопители и протокол

Сначала проверили пропускную способность TCP между Mac и контейнером с помощью `iperf3`:

```bash
iperf3 -c <IP_КОНТЕЙНЕРА>
iperf3 -c <IP_КОНТЕЙНЕРА> -R
```

Получилось **~714 Мбит/с** от Mac к серверу и **~897 Мбит/с** в обратном направлении. Сеть явно не ограничивалась 100 Мбит/с.

Затем отправили тот же ISO в тот же каталог через SCP (SSH/SFTP-подобный путь передачи):

```bash
time scp ~/Downloads/Win11_25H2_EnglishInternational_x64_v2.iso \
  user@<IP_КОНТЕЙНЕРА>:/srv/shlak/control.iso
```

Клиент показывал скорость порядка **69 МБ/с** во время передачи; общее время команды — **2:08,23**, то есть примерно **63 МБ/с в среднем**, включая накладные расходы. Передача происходила даже при другой параллельной операции копирования.

Эта проверка сильно сузила круг подозреваемых: локальное чтение ISO, сеть и само ZFS-хранилище могли обеспечить гораздо больше 11 МБ/с. Но это не означает, что все их особенности полностью исключены — разные протоколы предъявляют разную нагрузку.

## Что проверяли

| Эксперимент | Наблюдение |
|---|---|
| Исходный SMB, настоящий ISO | ~10–12 МБ/с |
| Отключение SMB Multichannel в macOS (`mc_on=no`) | Очень помогло ранним тестам, но **не устранило** медленную передачу настоящего ISO |
| `strict sync = no` только на тестовой шаре | Заметного ускорения ISO **не дало** |
| Временная настройка `signing_required=no` на Mac | macOS всё равно показывала `SMB_CURR_SIGN_ALGORITHM = AES_128_GMAC`; доказательств, что подпись действительно отключилась, не получили |
| `vfs objects = catia fruit streams_xattr` на тестовой шаре, `strict sync = no` | **2:20,27** на ~8,1 ГБ, около **58 МБ/с** |
| Те же VFS-модули, `strict sync = yes` | **2:38,08**, около **51 МБ/с** |
| Те же VFS-модули на основной шаре, стандартная синхронизация и восстановленный конфиг macOS | **2:29,90**, около **54 МБ/с** |

Промежуточные пиковые значения в мониторе активности достигали **~500–550 Мбит/с**. Для итогов использовали **полное время копирования**, а не мгновенную скорость.

## Конфигурация, с которой получилось ускорение

### 1. На macOS

В `/etc/nsmb.conf` оставили:

```ini
[default]
mc_on=no
```

У нас отключение SMB Multichannel значительно помогло на раннем этапе. **Это не универсальная рекомендация:** на нескольких физических интерфейсах Multichannel может быть полезен. Изменения `nsmb.conf` проверяйте после отключения и повторного подключения всех SMB-шар сервера.

Временный `signing_required=no` после эксперимента **удалили**: нет смысла ослаблять защиту, не получив подтверждённой пользы. На Mac при этом использовался SMB 3.1.1; шифрование SMB не было включено, согласованный алгоритм подписи отображался как AES-128-GMAC.

### 2. На Samba-сервере

Рабочая секция в `/etc/samba/smb.conf` после изменений:

```ini
[shlak]
   path = /srv/shlak
   browseable = yes
   read only = no
   guest ok = no
   valid users = shlak
   force user = shlak
   create mask = 0660
   directory mask = 2770
   vfs objects = catia fruit streams_xattr
```

Перед правкой разумно сохранить конфигурацию:

```bash
cp /etc/samba/smb.conf /etc/samba/smb.conf.before-fruit
```

Проверка и применение:

```bash
testparm -s
systemctl reload smbd
```

После этого **отключить и заново подключить SMB-шару на Mac**, чтобы пересоздать сеанс.

`strict sync = yes` оставили в стандартном значении; его можно проверить так:

```bash
testparm -sv 2>/dev/null | grep 'strict sync'
```

Не отключали ZFS `sync`, контрольные суммы или другие гарантии надёжности хранения.

### 3. Предупреждение `vfs_fruit`

`testparm` выдал:

```text
WARNING: some services use vfs_fruit, others don't.
Mounting them in conjunction on OS X clients results in undefined behaviour.
```

Причина: тестовая и основная файловые шары использовали `fruit`, а стандартные `[homes]`, `[printers]` и `[print$]` — нет. В этой сессии обе подключаемые с Mac файловые шары имели одинаковую VFS-конфигурацию; предупреждение **пока не устранено**. При дальнейшем обслуживании сервера стоит убрать ненужные стандартные шары или согласовать конфигурацию тех ресурсов, которые действительно будут одновременно доступны Mac. Не следует механически добавлять `fruit` ко всем служебным шарам.

## Как откатить изменение

Если после добавления VFS-модулей появились ошибки, на сервере можно восстановить предварительно сохранённый `smb.conf`:

```bash
cp /etc/samba/smb.conf.before-fruit /etc/samba/smb.conf
testparm -s
systemctl reload smbd
```

Затем отключить и подключить шару заново на Mac. Если экспериментировали с `/etc/nsmb.conf`, вернуть его собственную резервную копию и переподключить ресурсы.

## Выводы и ограничения

1. **Не путайте Мбит/с и МБ/с.** 90 Мбит/с — это около 11,25 МБ/с.
2. **Сравнивайте одинаковые данные.** Нулевой файл и настоящий ISO в ZFS с ZSTD дают принципиально разную нагрузку.
3. **Проверяйте транспорт отдельно от SMB.** `iperf3` и SCP помогли найти узкое место именно на SMB-пути.
4. В этом кейсе основной прирост совпал с добавлением **`catia fruit streams_xattr`**. Мы включили сразу три VFS-модуля и **не делали обратного A/B-теста**, поэтому нельзя строго доказать, какой модуль или сочетание параметров отвечает за улучшение.
5. Изменение `strict sync` само по себе не решило проблему. После включения VFS-модулей высокая скорость сохранилась при **стандартном `strict sync = yes`**.
6. **Не нужно отключать подпись SMB или надёжность ZFS наугад.** Наше ускорение сохранилось без таких уступок.

Итог на рабочей шаре: **~54 МБ/с вместо ~11 МБ/с** при передаче реального ISO. Это ещё не предел гигабитной сети, но уже пригодный для повседневной работы NAS.
